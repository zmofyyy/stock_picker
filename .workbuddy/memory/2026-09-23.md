## 缓存放开到全历史（用户需求「为什么选股指定日期选不了 22 年」）

**根因（三层收窄，每层都砍历史深度）**

| 层 | 位置 | 原设置 | 实际下界 |
|---|---|---|---|
| ① 源数据 | `vipdoc/*/lday/*.day` | 全历史（5605 只共 1701 万根，最早 1991-01-02） | 有 2022 ✅ |
| ② 内存缓存 | `config.json → cache_bars: 260` | 每只只留最后 260 根 | **2025-08-29** ❌ |
| ③ 日期控件 | `app.js` 写死 `/api/trade_dates?n=250` → `input.min` | 只报最后 250 个交易日 | **2025-09-12** ❌ |

迷惑点：缓存里唯一日期有 609 个（最早 2024-03-25），看着像有 2.5 年数据，
其实是 **3 只长期停牌股**各自「最后 260 根」的残影（2024-03-25 那天全市场只有 1 只有数据）。
判断可用区间要看「每天有多少只有数据」，不能只看 `date.min()`。

**用户决策**：问「放到多少」时，用户选 **「全部历史，现有数据什么时候开始就什么时候开始」**。

### 实现（1750 万行必须配 dtype 收缩）

实测规模：**17,012,754 行 / `bars.parquet` 360.4 MB / 内存 578.9 MB / 重建 18.8s**
（原 260 根口径：143 万行 / 39 MB / 175 MB / 8s）。

先扫全市场极值算 ULP 再决定 dtype（**这一步不能省**，见下表最后一行的反例）：

| 列 | dtype | 依据 |
|---|---|---|
| `code` | category(int16 码) | 2 字节/行；object 字符串约 54 字节/行 → **单列差 ~900MB** |
| `date` | int32 | YYYYMMDD 最大 8 位 |
| 价格 ×4 | float32 | 源是「分」网格；最大收盘 3275 元处 ULP 2.4e-4 < 0.005 |
| `amount` | float32 | 源本身 f4；最大 1.41e11 元处 ULP 16384 元，展示到「亿」3 位是 1e5 元 |
| `volume` | **uint32** | 源就是 u4（股）→ **无损**。**不能 float32**：最大 4.17e9 股处 ULP=256 股，前端「手」会偏 1~2 手 |
| `pct` | float32 | 相对量，但**计算**时用 float64 做完再降精度 |

**关键手法：per-frame 共享同一个 `CategoricalDtype`**（`read_many_bars`）。
若先 `concat` 成 object 字符串再 `astype("category")`，中间那步要多占 ~900MB。
`pd.Categorical.from_codes(np.full(len(df), idx, dtype="int16"), dtype=shared)` 是 O(1) 分配。

### 「不落列、按需实时算」（用户明确要求）

用户说「bar_index 和（bar_total）可以实时计算，需要时加载」。顺着这个原则把三个都去掉了：

- **`bar_index`** —— 全项目无人使用，直接不存。
- **`bar_total`** → `_category_bar_counts(upto)`：只在 5605 个类别上做一次 `searchsorted`，
  结果 22 KB（落列是 1700 万行 int64 = **136 MB**）。
  **语义要点**：按**锚点日**取值，不是「整段历史长度」—— 否则回看 2022 年时，
  2022-05 才上市的票会被误判成「K 线充足」。
- **`ma_vol` / `vol_ratio`** → `_attach_volume_stats(idx, window)`：
  原先对整张长表 `groupby().transform(rolling())`，要为 1700 万行建 2 个新列（**136 MB**）
  且跑一次全市场 rolling。其实选股只用**目标日期那几行** →
  改成 `该行在本股票切片内的序号 >= window` 才有效，均量取它前面 window 根
  求和范围只有 `行数 × window`（约 5605×20 = 11 万元素）。
  **float64 逐值精确**，实测与「从 .day 直接重算」完全一致。

选股过滤也改到**类别层**：`split_code` / 板块判定只对 5605 个类别算一次掩码，
再 `cat_ok[cat_codes]` 展开成行级布尔，避免 1700 万行逐行 `.map(dict)`。
历史日期选股实测 **0.11s**。

`_attach_volume_stats` 返回的小表把 `code` 还原成 `object` 字符串（最多 5605×lookback 行），
这样下游 `map` / `isin` / `itertuples` 全都跟以前一样是 str，没有 categorical 的边界情况。

### 二次踩坑与防复发

**1. 只比 mtime 的新鲜度判定会漏掉「配置口径变了」**
把 `cache_bars` 从 260 改成 0 后，旧缓存依然「比源数据新」→ 永不重建 → 日期控件还是老样子。
已在 `cache_freshness()` 里加口径比对：`meta["bars_per_code"] != config["cache_bars"]` → 判过期。
缺字段时取 `-1`，保证**老缓存（无此字段）也一定会重建**。

**2. 旧缓存读进来会让 `df["code"].cat.codes` 崩**
老 parquet 的 `code` 是 object 字符串。`bars()` 里加 `_coerce_bars_dtypes()`：
只对**不一致的列** astype，新缓存是 no-op，不会白复制 1700 万行。

**3. 前台 Bash 调用里起的 exe 会在该调用结束时被回收（严重误判）**
先前台 `nohup ./stock_picker.exe &` 起服务 → 调用返回 → 后续调用跑冒烟测试
→ **满屏红**：`/api/health` 失败、静态资源 `502 Bad Gateway`、`bootstrap 超时未就绪`。
我差点去查自己的代码。真相是进程被按**进程组**回收了（`nohup`/`&`/`disown` 都救不了）。
**正解：起服务 + 跑测试 + `taskkill` 收尾塞进同一次 Bash 调用。**
已写进 `local-shell-and-browser` 技能 5.4 节 + 自检清单第 7 条。
判断依据：① 服务日志只有启动那几行、没有任何 access log；② 报错是沙箱代理的 502 / 10061。

**4. `windows.psapi.GetProcessMemoryInfo` 静默返回 0**
要改用 `kernel32.K32GetProcessMemoryInfo`，且结构体首字段必须是 `DWORD`（不是 `c_ulong`）。

### 最重要的发现：`.day` 第 8 个 uint32（上日收盘）已失效

全市场抽样：**自 2015-12-16 起全部失效** —— 沪/深约 63~67% 的行是占位值 `65536`、
约 10% 是 `0`，有效值只存在于 2015 年及更早，**北交所从来没有**。
所以**不落缓存列**（否则多 68MB 常驻内存），涨跌停基准价一律用「前一根 K 线收盘」
（这也正是 stock_watch 实际在用的口径）。副作用：**省掉了一次 19s 的全量缓存重建**。

### 第二重要的发现：本机行情里 ST 股的涨跌幅带宽也是 10%，不是 5%

起因是测试报「`600753.SH ST海钦` 涨幅 8.41% 却被按 5% 判成涨停」。逐层查下去：

1. 名称表没错 —— `shs.tnf` 原始记录 `[81:89]` 确实写着 `ST海钦`，抽样 18 只（浦发/茅台/…）全对
2. 但这只票 2026-09-24 前的走势里，`20260720 -5.91%`、`20260730 -7.41%`、`20260914 +9.77%`，
   `20260923 high=13.60` **正好等于 `12.36×1.10` 的涨停价** → **带宽就是 10%**
3. 扩大到全部主板 ST 股：**144 只里 141 只（97.9%）**都出现过「最高价 > 前收 × 1.05」，
   占其交易日 8%~37%；`high/前收` 的 p99.9 **几乎全部 ≈ 1.10**
4. 兄弟应用 `streaks.py` 的 caption 也明写「**ST 股按常规板近似**」

**结论：`st_limit` 默认关闭**（service / app / 前端勾选框三处都改为默认 false）。
套用 5% 会把涨幅 5%~10% 的普通交易日错判成涨停 —— `2026-06-01` 一天就从 120 只变 168 只。
开关仍保留，供数据源确实带 5% 带宽时使用。

> 教训：**名称表里的「ST」前缀不等于 5% 带宽**。判定涨跌幅限制要看行情本身，
> 不能只信名称。以后遇到「名称与行情矛盾」的个案，先按数据反推事实，再决定口径。

### 实现要点（向量化，不逐股循环）

- `_streak_window()`：`(n_cat, window)` 右对齐矩阵 + `off = ends[:,None] - window + cols[None,:]`，
  展平成约 34 万行；避免 1700 万行 int64 落列
- 连板数：`boundary = (~lu) | (pos == 0)`；`streak_all = np.where(boundary, 0, gp - np.maximum.accumulate(np.where(boundary, gp, -1)))`
- 涨停因子按 **5605 个类别**算一次再 `factors[cat]` 展开到行
- 实测 **0.05~0.16s**（含 2015 / 2018 / 2022 等历史日期）

### 踩到的坑

**1. `boards` 传裸字符串会被拆成单字（静默失败）**
`[str(b) for b in "主板"]` → `['主','板']`，然后匹配不到任何板块、**返回空结果不报错**。
是我在测试里传了裸字符串才暴露出来。已加 `as_multi()`（支持 `,` / `，` / `、` / `;` / 空格），
并对**未知板块 / 未知交易所**明确报错（原来静默返回空）。这个失败模式很危险：不报错，只是没数据。

**2. 测试脚本自己有三处缺陷，被误当成产品 bug**
- `promotion` 是 `round(x, 4)`，断言容差却写 `1e-6` → 改成 `1e-4`
- `naive_streak()` 用 `limit_factor(code, name)` 的**默认值 True**（ST 5%），而 service 默认已改为 False
  → 对 ST 股会多数出一板（`000909.SZ` 差 1）。**独立实现与主实现的口径必须显式对齐**
- `extra` 用带市场前缀的 `sh600753`，`st_codes` 却不带前缀 → 差集恒非空
- `limit_prices(10.15, 110)` 标量入参 → `_to_cent` 返回 0 维数组，`lup[0]` 抛 `IndexError`
  → 已让 `_to_cent` 返回 `np.atleast_1d(...)`，标量入参也安全

**3. 快照数量观察**：`persist_test.py` 与 `smoke_test.py` 各自的备份仍会留在 `dist/data/backups/`，
不含用户数据，先留着。

### 环境发现：PowerShell `Start-Process` 起的服务能跨调用存活

以前记的结论是「前台 Bash 调用里起的服务会在该调用结束时被按进程组回收，
所以『起服务 + 测试 + 收尾』必须塞进同一次 Bash 调用」。这次发现更好的做法：

```powershell
Start-Process -FilePath "dist\stock_picker.exe" -ArgumentList '--no-browser','--port','8778' -WorkingDirectory "dist"
```

这样起的进程**独立进程树**，后续多次 Bash / PowerShell 调用都能访问它 ——
于是浏览器自动化可以分多步慢慢做（open → 点页签 → eval 读数 → 截图 → close），
不必挤在一次调用里。收尾用 `taskkill //F //IM stock_picker.exe`。
（注意：`agent-browser` 没有 `resize` 命令，视口尺寸不能改。）
